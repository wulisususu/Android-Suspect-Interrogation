# Qwen3-4B 实时语音归档到正式笔录设计

## 1. 背景与目标

当前系统已经具备实时语音采集、FunASR 转写、说话人识别、原始对话留存、正式笔录模板、动态问题、QuestionRound 与人工修订能力，但“实时语音如何进入左侧正式笔录”主要依赖确定性问题识别与 regex/alias 精确匹配。

该机制在真实询问场景中存在明显限制：民警通常不会逐字复述模板问题；同一问题可能有多种口语表达；现场会出现模板外问题；追问可能属于同一正式问题；大量无效话语不应进入正式笔录。

本设计引入本地 Qwen3-4B 作为“问答归档路由器”。模型不直接操作数据库，不凭空生成询问事实，而是在完整真实问答单元基础上判断应归入何处，并对真实问题与回答做受约束的书面化整理。

目标：

1. 民警与嫌疑人自然对话即可形成左侧正式笔录，不要求逐字念模板。
2. 固定模板问题、已有案件动态问题、现场新增真实问题均可自动归档。
3. 同一语义问题的多轮追问合并为一个正式问答项。
4. 无法可靠归档的问答进入人工待处理区，并支持拖拽处置。
5. 废话、流程性话语、明显答非所问等不自动进入正式笔录。
6. 右侧原始对话与原始 ASR 事实流始终完整保留，不被 AI 整理结果覆盖。
7. 模型只做分类、匹配与受约束的口语书面化，不得补充原始语音中不存在的事实。

## 2. 核心原则

### 2.1 原始事实流不可变

右侧实时对话是原始事实流。所有 ASR fragment、说话人、时间范围、识别修订与来源关系继续独立保存。

AI 归档只产生正式笔录投影，不删除、不重写、不覆盖原始对话。

### 2.2 问题必须来自真实民警语音

现场新问题的来源必须是实际出现过的民警语音。

Qwen3-4B 可以对该真实问题做轻度书面化，但不得凭空创造一个民警没有问过的问题，也不得增加新的指控、动机、时间、人物、地点或因果关系。

示例：

- 原话：`你咋又回去了？`
- 允许：`你为什么又返回现场？`
- 不允许：`你返回现场是否为了实施报复？`

### 2.3 回答只允许忠实整理

模型允许：

- 删除“嗯、啊、这个、那个”等无意义口头语；
- 合并重复表达；
- 消除明显口头重复；
- 保留自我修正后的最终表达；
- 在不改变含义的前提下调整语序和书面表达。

模型禁止：

- 补全未说出的具体时间；
- 补全未出现的人名、地点、数量；
- 替嫌疑人推断动机；
- 把模糊陈述变成确定事实；
- 擅自解决前后矛盾；
- 把推测改写为事实。

示例：

- 原话：`嗯，应该是八点多吧，我也记不太清，大概八点十几分这样。`
- 允许：`大概在晚上八点十几分，具体时间记不清。`
- 不允许：`晚上8时15分到达现场。`

## 3. 问答单元 QA Unit

模型不按单个 ASR fragment 工作，而按完整问答单元工作。

一个 QA Unit 至少包含：

- 真实民警提问 fragment 集合；
- 随后的嫌疑人回答 fragment 集合；
- 对应时间范围；
- 原始 speaker attribution；
- 原始文本；
- 最近上下文；
- 当前正式问题集合。

典型封口规则：

1. 检测到民警有效提问，开启 QA Unit。
2. 后续嫌疑人回答持续追加到当前 QA Unit。
3. 再次检测到民警新的有效提问时，封口上一 QA Unit，并开启下一组。
4. 审讯停止、长时间静音、人工结束当前轮时，也可封口当前 QA Unit。

模型应同时看到最近 1~2 轮上下文，以判断“这是新问题还是对上一问题的追问”。

## 4. A/B/C/D/E 分类

模型必须输出且只能输出以下五种业务分类之一。

### A — MATCH_FIXED

当前真实问答对应已有固定模板问题。

系统动作：

1. 保留模板原问题文本作为左侧 `问：`。
2. Qwen 只整理真实嫌疑人回答。
3. 写入该正式问题。
4. 如果该问题已有历史回答，则按“同一语义问题合并”规则更新正式答案。

示例：

固定模板：`你因何事来公安机关？`

真实语音：

- 民警：`今天为什么过来的？`
- 嫌疑人：`昨天晚上跟别人发生了一点冲突，派出所今天通知我过来配合调查。`

左侧：

- 问：`你因何事来公安机关？`
- 答：`昨天晚上与他人发生冲突，今天接到派出所通知后前来配合调查。`

### B — MATCH_EXISTING

当前真实问答对应已有案件动态问题（CASE 或 LIVE）。

系统动作与 A 相同：保留左侧已有问题原文，只整理答案并写入。

示例：

已有动态问题：`你与王某是什么关系？`

真实语音：

- 民警：`你以前跟王某熟不熟？`
- 嫌疑人：`认识三四年了，以前一起干过活。`

左侧：

- 问：`你与王某是什么关系？`
- 答：`与王某认识约三四年，之前曾一起工作。`

### C — CREATE_LIVE_FROM_SPEECH

当前民警真实提出了有效问题，但固定模板和已有动态问题中没有合适目标。

系统动作：

1. 使用真实民警问题作为来源。
2. 对真实问题做轻度书面化。
3. 对真实嫌疑人回答做忠实书面化。
4. 新建 `source=LIVE` 的正式问题。
5. 立即写入正式答案。
6. 新问题按民警实际提问发生顺序插入正式笔录。

示例：

真实语音：

- 民警：`你离开现场以后有没有又回来？`
- 嫌疑人：`回来过一次，我手机落里面了。`

左侧新增：

- 问：`你离开现场后是否再次返回？`
- 答：`返回过一次，因为手机遗留在现场。`

AI 不能创建真实语音中不存在的问题。

### D — NEEDS_REVIEW

当前问答可能有业务价值，但模型无法可靠判断：

- 应匹配哪个正式问题；
- 是否属于上一问题的追问；
- 是否应新建现场问题；
- 回答与问题的对应关系是否足够明确；
- 内容存在矛盾或其他高风险歧义。

系统动作：

1. 不自动写入正式笔录。
2. 右侧将整个 QA Unit 高亮为“待处理”。
3. 展示原始问题、原始回答、AI 建议与候选目标，但不自动提交。
4. 支持民警拖拽处置：
   - 拖整组 `问题 + 答案` 到左侧空白/指定位置：创建 LIVE 问题并写入回答；
   - 拖整组 `问题 + 答案` 到已有正式问题：将其作为该问题新的历史轮次，并合并正式答案；
   - 只拖 `答案` 到已有正式问题：仅把回答关联到目标问题，不创建新问题；
   - 保持未处理：继续停留在 D 状态；
   - 明确忽略：转为 E/人工忽略状态，但原始对话不删除。

D 类人工处置后，正式笔录中的插入位置默认按该 QA Unit 原始发生时间恢复，而不是按人工处理时间排到末尾。

### E — IGNORE

内容不应自动进入正式笔录，包括但不限于：

- 寒暄；
- 操作性话语；
- “继续说”“声音大一点”等流程指令；
- 无实质内容的应答；
- 明显答非所问；
- 与案件或正式询问无关的闲聊；
- 无法形成有效问答关系且无归档价值的内容。

系统动作：只保留右侧原始对话，不自动进入左侧正式笔录。

E 不等于删除。它只是“正式笔录不自动归档”。

## 5. 同一语义问题的多轮追问合并

同一语义问题在左侧只保留一个正式问题和一个合并后的正式答案。

示例：

真实语音：

- 民警：`你几点到现场？`
- 嫌疑人：`大概八点多。`
- 民警：`具体一点呢？`
- 嫌疑人：`应该八点十五左右。`

模型判断第二轮属于对上一问题的追问。

左侧：

- 问：`你几点到现场？`
- 答：`大概在八点十五分左右。`

底层仍保留多个历史 QuestionRound/QA Unit：

- Round 1：原始问题 + 原始回答；
- Round 2：追问 + 追加回答；
- 正式展示层：merged formal answer。

### 5.1 合并约束

模型可以：

- 去重；
- 合并补充信息；
- 用后续更具体但不矛盾的信息替代前面的模糊表达。

模型不可以：

- 擅自选择两个矛盾说法中的一个；
- 隐藏明显改口；
- 把不一致内容强行融合为确定事实。

遇到明显矛盾时应优先输出 D — NEEDS_REVIEW。

## 6. 正式笔录顺序

正式笔录 BODY 区的业务顺序以民警真实提问发生顺序为主。

设计上区分：

- `CaseQuestion`：问题的语义实体；
- `QuestionRound / QA Unit`：某次真实发生的问答；
- 正式展示顺序：由第一次有效提问的时间锚点决定，而不是单纯依赖模板原始 sort_order。

A/B 命中已有问题时，如果该问题第一次在本次正式询问中被实际问到，则其展示位置按首次实际提问时间确定。

C 新现场问题按实际发生位置插入。

D 后续人工处理时恢复到原始发生时间位置。

同一语义问题后续追问不会重复在左侧创建第二个问题，而是继续合并到原问题。

固定 OPENING/CLOSING 法定区块仍保持受保护边界，不因 BODY 排序规则而破坏模板结构。

## 7. Qwen3-4B 输入

每个待路由 QA Unit 的模型输入应包含：

1. 当前真实民警问题原文；
2. 当前真实嫌疑人回答原文；
3. 当前 QA Unit 的 fragment IDs 与时间范围；
4. 最近 1~2 轮 QA 上下文；
5. 当前已有正式问题列表：
   - id
   - text
   - source: FIXED/CASE/LIVE
   - section
   - 是否已有回答
6. 当前正在讨论/最近命中的正式问题；
7. 严格的事实保真与书面化规则。

问题数量较少时可以直接给出全部正式问题；若案件问题数量明显增大，可以增加 deterministic candidate retrieval，仅把 Top-N 候选交给 Qwen，但不能牺牲 CREATE_LIVE 与 NEEDS_REVIEW 分支。

## 8. Qwen3-4B 结构化输出

模型不得返回自由文本作为业务控制结果。必须返回可校验 JSON。

建议结构：

```json
{
  "classification": "MATCH_FIXED | MATCH_EXISTING | CREATE_LIVE_FROM_SPEECH | NEEDS_REVIEW | IGNORE",
  "target_question_id": "existing-question-id-or-null",
  "formal_question": "only-for-C-or-null",
  "formal_answer": "formalized-answer-or-null",
  "related_to_previous": true,
  "confidence": 0.94,
  "candidate_question_ids": [],
  "flags": ["CONTRADICTION", "LOW_CONTEXT"],
  "reason_code": "SEMANTIC_MATCH"
}
```

`reason_code` 使用枚举，不依赖自然语言解释参与业务逻辑。

## 9. 确定性提交层

Qwen3-4B 只输出 `RoutingDecision`，不能直接写数据库。

新增确定性后端服务建议命名：

`FormalRecordRoutingService`

职责：

1. 校验 case、session、question、QA Unit 是否存在且属于同一案件；
2. 校验正式笔录未冻结；
3. 校验模型 classification 与字段组合是否合法；
4. 校验 A/B 的 target question 存在且 active；
5. 校验 C 必须有真实 officer fragment 来源；
6. 校验 C 的 formal_question 只能来源于真实问题，不允许无来源创建；
7. 记录 raw -> formal provenance；
8. 保证 fragment/QA Unit 幂等，防止重复归档；
9. 执行 QuestionRound 创建、合并、LIVE 问题创建或 D/E 状态落库；
10. 发布正式笔录更新事件。

## 10. 建议的数据模型

新增 `qa_units`：

- id

- session_id
- sequence_no
- started_at_ms

- officer_fragment_ids_json
- suspect_fragment_ids_json
- raw_question
- raw_answer

- created_at
- updated_at

新增 `qa_routing_decisions`：

- id
- qa_unit_id
- model_id
- model_version
- prompt_version
- classification
- target_question_id
- formal_question
- formal_answer
- confidence
- candidate_question_ids_json

对于合并答案，建议保留每次模型输出/人工修订历史，不覆盖历史来源。

## 11. D 类拖拽交互

### 11.1 右侧展示

D 类 QA Unit 在右侧作为一个不可拆散的默认卡片高亮：

- 民警真实问题；
- 嫌疑人真实回答；
- “AI 无法可靠归档”；
- 可选候选问题；
- 拖动手柄；
- “仅拖答案”子操作。

### 11.2 拖整组到已有问题

含义：人工确认“这整组问答属于这个正式问题”。

系统：

- 保存真实问题作为历史轮次；
- 保存真实回答来源；
- 对回答做受约束的正式化或使用当前 AI 建议文本；
- 合并进目标问题正式答案；
- 标记 routing source = MANUAL_DRAG_MATCH。

### 11.3 只拖答案到已有问题

含义：人工确认回答属于某正式问题，但当前民警问句本身不需要成为正式问题。

系统：

- 只关联 suspect fragments/answer；
- 不把 officer question 写成新的正式问句；
- 标记 routing source = MANUAL_DRAG_ANSWER_ONLY。

### 11.4 拖整组到左侧空白位置

含义：人工确认这是一个新的有效现场问答。

系统：

- 真实问题经过受约束的书面化后创建 LIVE 问题；
- 回答写入；
- 按 QA Unit 原始时间插入；
- 标记 routing source = MANUAL_DRAG_CREATE_LIVE。

## 12. 前端实时反馈

右侧每个已封口 QA Unit 应显示明确状态，消除当前黑盒体验：

- `✓ 已归档 → 你因何事来公安机关？`
- `✓ 已归档 → 现场问题：你离开现场后是否再次返回？`
- `↻ 正在判断归档位置`
- `⚠ 待人工处理`
- `— 未进入正式笔录`

A/B/C 自动归档成功后，前端必须收到正式笔录已更新事件，不依赖固定 90ms 延时猜测 projection 是否完成。

建议后端顺序：

1. 原始 fragment/QA Unit 落库；
2. Qwen 路由；
3. FormalRecordRoutingService 提交；
4. transaction commit；
5. 发布 `FORMAL_RECORD_UPDATED`；
6. 前端刷新左侧正式工作区。

原始 `ASR_FRAGMENT` 事件仍可独立用于右侧即时显示。

## 13. Qwen 不可用与错误处理

Qwen3-4B 不可用时：

- 原始语音、ASR、右侧对话继续工作；
- QA Unit 继续封口；
- 新 QA Unit 默认进入 `NEEDS_REVIEW`，或按后续明确配置选择 deterministic legacy fallback；
- 不应因为 LLM 不可用而停止录音或丢失原始事实流。

不允许 Qwen 调用失败后静默丢弃 QA Unit。

模型 JSON 解析失败、target question 不存在、输出字段不合法等均进入受控 D 状态并记录错误原因。

## 14. 与现有 regex 逻辑的关系

现有 `question_matching.py` 的 regex/alias 机制保留，但角色调整为：

- 可作为快速候选召回；
- 可作为 Qwen 不可用时的 deterministic fallback；
- 不再作为正常生产路径中决定是否进入左侧正式笔录的唯一依据。

现有 `InterrogationProjectionService` 应逐步从“单 fragment 直接决定正式归档”重构为：

`ASR Fragment -> QA Unit Builder -> Qwen Router -> FormalRecordRoutingService`

## 15. 审计与可追溯性

每个左侧正式问答必须可追溯到：

- 原始 officer fragment IDs；
- 原始 suspect fragment IDs；
- QA Unit；
- Qwen routing decision；
- 使用的 model/version/prompt version；
- 自动或人工路由来源；
- 后续人工修改历史。

任何 AI 整理结果都不能成为唯一事实副本。

## 16. 安全边界

1. 模型不得直接访问数据库写接口。
2. 模型不得新增不存在于语音事实中的案情。
3. 模型不得自动处理明显矛盾，应转 D。
4. 模型不得修改已冻结/已签名笔录。
5. 模型输出必须经过 schema 与业务规则双重校验。
6. 不因自动归档删除右侧原始记录。
7. D 类人工操作必须形成审计事件。

## 17. 验收标准

### 17.1 A 固定模板

民警使用与模板不同但同义的自然说法，系统能正确匹配固定问题，并将整理后的嫌疑人回答自动写入。

### 17.2 B 动态问题

已有 CASE/LIVE 问题可被自然语言同义问法正确匹配。

### 17.3 C 现场新问题

真实民警提出模板外问题时，系统能基于真实问题创建 LIVE 问题，并将真实回答整理后写入；不得生成未实际提问的问题。

### 17.4 多轮追问

对同一问题的多轮追问不创建重复正式问题，正式答案合理合并；原始轮次仍完整可追溯。

### 17.5 D 待处理

不确定问答不会自动污染正式笔录；民警可以拖整组或只拖答案完成归档，并恢复到原始发生位置。

### 17.6 E 无效内容

操作性话语、寒暄、废话、明显答非所问不会自动进入左侧。

### 17.7 故障降级

Qwen3-4B 停止或返回非法输出时，录音、ASR、原始对话仍正常，相关 QA Unit 不丢失。

### 17.8 真机验收

必须在 RK3588 真机上用真实 FunASR + 实际麦克风完成 A/B/C/D/E 和多轮追问的端到端测试，不能只以 hosted CI 或 mock E2E 作为验收依据。

## 18. 非目标

本阶段不做：

- 让 Qwen 自由撰写整篇正式笔录；
- 让 Qwen 自行创造未发生的询问问题；
- 用 LLM 替换原始 ASR 事实流；
- 自动删除 AI 判断为 E 的原始语音记录；
- 用云端模型作为生产必需依赖；
- 在模型不确定时强行选择一个正式问题。

## 19. 推荐实施边界

建议分成以下独立单元，避免继续扩大现有 `AsrCaptureService`、`InterrogationProjectionService` 和前端 store 的职责：

1. `QaUnitBuilder`：只负责从已确认 speaker 的 final fragments 形成 QA Unit。
2. `QwenFormalRecordRouter`：只负责构造模型输入、调用本地 Qwen3-4B、解析结构化输出。
3. `FormalRecordRoutingService`：只负责确定性校验和数据库提交。
4. `FormalAnswerMerger`：只负责同一问题多轮答案的受约束合并。
5. `ManualRoutingService`：只负责 D 类拖拽后的人工路由动作。
6. 前端 `QaRoutingCard/ReviewQueue`：只负责展示状态、候选项和拖拽交互。

上述边界是后续实现计划的基础。
