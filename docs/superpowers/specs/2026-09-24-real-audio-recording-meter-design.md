# 实时录音波形与真实录音时长

Date: 2026-09-24  
Branch: `linux-adaptation`  
Status: 用户已批准规格，实施完成

## 1. 目标

在右侧实时对话面板的聊天记录区域顶部，横向显示真实麦克风输入波形；录音按钮准确显示录音时长。波形必须来自实际采集到的音频样本；静音应显示为接近基线的真实平直信号，采集停止或输入中断时不得用动画补造波形。浏览器麦克风和开发板麦克风使用同一显示能力。

## 2. 当前问题

实时对话区的按钮使用 `captureElapsedMs` 格式化时长。前端只有在捕获状态含有 `startedAt` 时才计算时间，但后端活动录音的 `_runtime_status()` 没有返回该字段；停止状态才返回数据库中的开始时间，因此活动期间按钮持续显示 `00:00`。

两种麦克风输入最终都进入后端 `AsrCaptureService._capture_loop()`。当前循环读取 PCM 并送入实时语音协调器或本地识别队列，但没有发布音量测量事件；前端因此没有可信波形数据。

## 3. 方案

### 3.1 采集与测量

- 在共享后端采集循环中对实际收到的 PCM16 样本计算 RMS 和峰值。测量仅保留数值，不新增原始音频副本，也不改变录音归档、ASR 或声纹处理顺序。
- ALSA 开发板麦克风与浏览器麦克风都从该共享采集入口测量，因此前端不另开一条浏览器麦克风分析链路。
- 以实际 PCM 到达作为发出测量的前提，将 `AUDIO_LEVEL` 事件限制在约每秒 10 次以内。事件包含案件 ID、捕获会话 ID、累计采样数、采样率、RMS 和 peak；采集不到音频时不产生虚构数值。
- 前端只接收当前案件和当前捕获会话的测量事件，并保留有限长度的最近测量序列。新捕获会话开始时清空旧波形；历史或其他会话的事件不得污染当前波形。

### 3.2 时长

- 活动态状态响应补齐数据库记录的捕获开始时间，并与停止状态使用相同时间格式。
- 前端继续按开始时间和当前时钟计算经过时长，录音中的按钮显示 `MM:SS`；停止后按钮恢复“开始录音”，下一次新录音从 `00:00` 重新计时。
- 录音时长表示录音会话已运行的实际时间，不根据声音大小跳变；波形才反映真实 PCM 能量。这样静音期间计时仍继续，而波形保持安静。

### 3.3 界面

- 在右侧聊天记录顶部增加横向铺满的波形区；聊天记录滚动时波形固定在记录区上沿。视觉参考用户提供的时间轴波形示例，并维持实时对话面板的现有布局风格。
- 波形柱高由 RMS/peak 样本映射产生，零值保持基线；不使用 CSS 呼吸动画、随机高度或预制循环数据。
- 录音刚启动尚无首个音频测量时显示等待输入状态。连续一段时间无新 PCM 时停止波形更新并明确呈现无新音频信号；录音停止时波形进入静止状态。
- 录音未运行时隐藏或清空活动波形，避免用户误以为设备仍在采集。

## 4. 范围与非目标

本次仅调整实时录音的状态时间字段、实际 PCM 音量事件、前端状态归约及右侧聊天记录区域的波形显示。案件音频长期保存、转写、声纹分析、设备选择和录音生命周期策略均沿用现有实现。波形用于反馈输入活动，不承诺声学质量评估或说话人识别。

## 5. 验收标准

1. ALSA 与浏览器麦克风产生的波形都来自后端实际收到的 PCM；静音呈现真实低幅度，断流不会继续跳动。
2. 录音开始后按钮时长从 `00:00` 开始递增；停止后按钮恢复开始状态，新录音重新计时。
3. 活动捕获状态包含有效开始时间；丢失的会话/案件事件不会改变当前界面。
4. 波形测量事件经过频率限制，前端序列有界，不保存音频内容。
5. 现有录音、实时转写及音频归档行为保持兼容。

## 6. 实现触点与验证

- 后端：`linux/backend/app/services/asr_capture_service.py` 的活动状态与共享 PCM 采集循环。
- 前端：`webapp/src/types/interrogation.ts`、`webapp/src/stores/interrogation.ts`、`webapp/src/components/LiveDialoguePanel.vue` 及其样式。
- 验证覆盖已知 PCM 的 RMS/peak、事件节流与会话过滤、开始时间和停止状态、波形静音/断流呈现；并运行相关后端与前端检查。
